## Request

Recreate [Pele](https://github.com/obsidianmd/pele) in Swift so Mermaid diagrams render natively on iOS, iPadOS and macOS. Pele is Obsidian's Mermaid renderer, written in TypeScript. It reads every diagram type built into Mermaid 12.1.0, uses its own layout and visual style, and draws SVG. Its README claims, as given by the owner:

- 100–500× faster than mermaid.js
- 6× smaller bundle
- No dependencies
- Easy to theme
- Responsive to device width

| Pele (TypeScript) | Value |
|---|---|
| Bundle size | 230 kB |
| Render time | 0.05–0.3 ms |
| Dependencies | 0 |

Because Graphite's version is native, it has to beat these numbers by a wide margin, not match them.

## Performance targets

Targets to meet before the feature counts as done. Each number is measured, never estimated, and recorded in `Coverage.md` with the machine, the build configuration (Release) and the input set.

| Metric | Pele | Graphite target | Stretch |
|---|---|---|---|
| Render time, parse + layout, per diagram | 0.05–0.3 ms | 10× faster: 5–30 µs | 50× faster: 1–6 µs |
| Size added to the app binary, all diagram types | 230 kB | 4× smaller: ≤ 60 kB per architecture | ≤ 30 kB |
| Dependencies | 0 | 0: no WebKit, no JavaScriptCore, no Swift packages | |
| Drawing on screen | SVG in the DOM | Core Graphics / Core Text on the main thread, no dropped frames while scrolling a note full of diagrams | |
| Memory per diagram | not stated | ≤ 64 kB for layout data of a typical diagram | |
| Theme change | CSS variables, no re-render | Redraw with the new colors without parsing or laying out again | |
| Width change | Layout adapts to the container | Layout again only, without parsing again, within one frame | |

Rules for the comparison:

- Compare on the same inputs: Pele's benchmark set (`npm run bench`) and the diagrams of the Mermaid 12.1.0 specs, run on the same Mac. Pele's README gives no measuring method, so run its benchmark ourselves and record its numbers next to ours.
- Measure parse, layout and drawing separately, and report the median and the 99th percentile.
- Measure on the owner's iPad Pro M1 and an iPhone too, not only on the Mac.
- Measure binary size as the difference in the Release app's executable with and without the diagram module, per architecture.
- Size, the owner 2026-11-19: the package's 1.3 MB in the iOS app (`Docs/App-size-todo.md`, measured 2026-10-24) is accepted as its target, in place of 60 kB per architecture.

## Decisions (2026-10-22)

1. **The code is a standalone package, `Packages/MermaidDiagrams`** (since 2026-11-19 the repository [Graphite-Note/MermaidDiagrams](https://github.com/Graphite-Note/MermaidDiagrams), MIT licensed with its history, which Graphite depends on by version: the owner's choice that day) (`Docs/solid/rewrite-foundations.md` section 3.5, `FR-110`), like `Packages/NotebookImport`. It reads Mermaid text, lays the diagram out and draws it into any `CGContext`, and knows nothing of Graphite: no vault, preference, logger or Graphite type, and limits and fonts are parameters. It imports Foundation, CoreGraphics and CoreText only (no UIKit, AppKit or SwiftUI), so it builds and tests alone on the Mac. Inside it: one folder per diagram type (`Flowchart/`: model and parser), and the parts the types share: `Layout/` (a layered graph layout over plain values, which the graph-shaped types such as state, class and ER diagrams will use too), `Text/` (label measuring and wrapping) and `Drawing/` (the renderer, given a palette of colors). Graphite's reading view is the one module that imports it.
2. **One package with one library, not one module per diagram type** (the first open question). Statically linked Swift code cannot be loaded on demand on iOS, so a module per type would save nothing at run time; the types share their layout, text and drawing code, which separate modules would duplicate or split further. The size target is met by keeping each type small and by dead-code stripping, measured as the targets above say.
3. **Pele's visual style, Graphite's fonts and colors** (the second open question). Shapes, their padding, the spacing between nodes and ranks, the arrowheads, the S-curved edges and the patch behind an edge label follow Pele, so a vault looks the same in Obsidian and in Graphite. The text is the note's font at the note's text size, and the colors come from the note's appearance: light or dark, and the vault theme's background, text and accent where it sets them. The `--pele-*` variables of an Obsidian theme or snippet stay in the theme item below.
4. **The first type is the flowchart** (`flowchart` and `graph`): the type notes use most, and the one most others build on, since state, class and ER diagrams are graphs laid out the same way. The first slice reads the direction, the classic node shapes (`[ ]`, `( )`, `([ ])`, `[[ ]]`, `[( )]`, `(( ))`, `((( )))`, `> ]`, `{ }`, `{{ }}`, `[/ /]`, `[\ \]`, `[/ \]`, `[\ /]`) and `@{ shape: … }` with those shapes' names, quoted and Markdown labels and entity codes, edges (arrow, open, dotted, thick, invisible, circle and cross ends, both ways, longer edges, labels in both syntaxes), chains and `&`, `%%` comments, and `accTitle` and `accDescr`. It reads but does not apply styles (`classDef`, `class`, `:::`, `style`, `linkStyle`) and `click`. A flowchart with a `subgraph` stays shown as code until clusters are laid out: drawn without its boxes, it would look complete and be wrong.
5. **The reading view draws it; the main actor only draws.** Core splits a ` ```mermaid ` fence into a block of its own, as it does a ` ```base ` fence, unless a community plugin draws `mermaid`. The reading view's builder, which already runs off the main actor, parses the diagram and lays it out at the note's text size. The view paints what the package prepares (`FlowchartDrawingParts`: paths by stroke and fill, and placed text) as SwiftUI shapes and text, in the colors of the moment, so a theme change paints again without parsing or laying out again. It does not use a SwiftUI `Canvas`: a canvas starts a graphics device that held about 200 MB while a note scrolled (`Docs/Coverage.md`, 2026-10-21), and shapes stay vector in a printed PDF. The package's own Core Graphics renderer draws the same parts into a bitmap or a PDF context. In this slice a diagram wider than the column is scaled down to fit, and one laid out at another text size than the note's now is drawn in proportion until the note is built again; laying it out again for the width is the width item. A diagram type not drawn natively yet stays shown as code, as today, and a flowchart that cannot be read shows why under its source.
6. **Live Preview comes next, through the same view.** `LivePreviewBlockScanner` gets the same block kind, and `LivePreviewRenderedBlocks` draws the same diagram view over the concealed fence, showing the source when the cursor enters the block, as it does for math, bases and tables.
7. **Diagrams are part of the reading view, not a switchable feature.** The reading view is in the kernel (`rewrite-foundations.md` decision 16), and Obsidian has no switch for Mermaid either. Nothing is built at launch: the package does work only for a note that has a ` ```mermaid ` block, and its only state is the text measurer each reading build makes and drops (`FR-109`).

## Decisions (2026-11-19, MermaidDiagrams 0.2.0)

8. **One preparation and one painter.** `ReadingDiagram` is `drawn(PreparedMermaidDiagram)` or `unreadable(source, MermaidDiagramPreparationFailure)`, made by one `MermaidDiagramPreparation.prepare` call with `WallClock`'s moment and time zone; `ReadingDiagramScenePainting` paints any type's `DiagramScene` as SwiftUI paths (a `LinearGradient` over the page for a gradient) and one `Text` per line, still no `Canvas` (decision 5). `ReadingDiagramFailure` became the package's `MermaidDiagramPreparationFailure`; Graphite keeps its English sentences, its theme colors, the "styling not applied" line and the source shown with `ObsidianMarkdownText`.
9. **A type the package adds needs no Graphite code.** Nothing in Graphite switches over the diagram types: the label a screen reader hears without a title is the package's `MermaidDiagramKind.spokenName`, and the sentences for a refusal and for a syntax problem switch over an optional, so a refusal or problem the package adds later is worded by its kind (`MermaidDiagramPreparationFailure.Category`) or as "a statement is not written as its diagram type reads it" instead of breaking the build (every warning is an error in Graphite, and a switch that lists every case cannot have a default).
10. **Where Pele and the 0.1.0 reading views differed, Pele.** The scenes paint as Pele does; the reading views of 0.1.0 differed in five places, none of them a deliberate fix (`git log -S` finds each in the commit that first drew its type, 1cbf1cb1, 29aa66f8, c4c51ea0 and 9ab113a7 of 2026-10-23, and the class colors' file was written there too): a sequence diagram's number badges, a class diagram's lines and marks, and a user journey's score line and faces are in the line role (`--pele-line`, the text color unless a theme sets it) where the views used the text color; a quadrant chart's quadrant labels are painted under its points, where the view painted them over; a class diagram's annotations, cardinalities and note surface take the palette's muted and second surface roles (the theme's muted text and `--pele-surface-alt` where set) where the view mixed 64.7 % and 11.2 % of the way from the page to the text. Without a theme setting those variables only the quadrant order shows, where a point lies on a label. Text is centered by its own width as the views set it (the package's Core Graphics renderer starts each line at its measured start, which leans a bold title right, since the lines are measured in the regular font); a class's members, which the old view set from their left edge, may start up to a pixel apart.

## Redesign (MermaidDiagrams 0.8.0)

Issue: [#225](https://github.com/Graphite-Note/Graphite/issues/225)

The owner, 2026-11-24, choosing how to go after the ten-times target the Speed items above missed: "Redesign reading and SVG". A design phase measured MermaidDiagrams 0.7.0 (main de81532, Apple M5 Max, Release) and prototyped each stage; its five documents and prototype code are on the package's branches `redesign-prototype-reading`, `-layered-layout`, `-text-and-labels`, `-scene-and-svg` and `-slow-types` (`docs/redesign/<area>.md`). On Pele's 114 flowchart examples today's reading takes 3.5 µs, layout 7.2 and the SVG 5.6, against Pele's 22.1 µs render; about 55 % of the sampled time is Swift's own overhead (retain and release 25 %, malloc, free and array growth 28 %, hashing and generic metadata), so the redesign changes the data, not the algorithms: flat arrays of small structs, labels as byte ranges of the source, identifiers interned, one reused per-thread scratch, the SVG written into one byte buffer, and accessibility text made only when read, every output byte for byte the same. Measured in the prototypes: the flat flowchart reader 3.5 → 0.72 µs (4.9 times; trees and meshes 7 times), the layered ranking on an arena 7 to 9 times, text measured and wrapped on bytes 4 to 6 times (widths identical to the bit), the byte SVG writer 1.7 to 3 times (identical on 2,246 documents). Expected, from those: reading and layout ten times Pele reachable or close on most types, 10 to 35 % short on C4, swimlane and agent flow; with the SVG four to seven times, since writing a journey's 1,057 numbers alone takes longer than a tenth of Pele's render. The waves below are built by parallel agents, each package reviewed and merged in turn; Graphite stays on 0.7.0 until 0.8.0 is released.

- [ ] Wave 1, the foundations: the reading front end that copies nothing and the flat flowchart reader and model (FlowchartDiagram kept as a view over it); the per-thread scratch arena and the flat layered layout on spans for every type that uses it; text decoded, measured and wrapped on bytes with accessibility made when read; the SVG written into one reused byte buffer. Started 2026-11-24.
- [ ] Wave 2, the flowchart end to end and the scene: the compound and cluster layout on spans, the flowchart's measurement and page assembly on spans; the scene stored as flat path lanes (no CGPath until painted), its builder, renderer and shared drawing helpers, the flowchart's scene; style statements on bytes; front matter, configuration and theme colours read once and resolved when used; scene text from bytes.
- [ ] Wave 3, every other type: byte readers for C4, agent flow and use case (their UTF-16 columns made only when asked) and the Langium types' tokenizer compiled; flat readers and layouts for the journey, block, quadrant, XY chart, Gantt, requirement, kanban and swimlane; the state, class, entity relationship, requirement and use case layouts on spans; each family's scene on path lanes.
- [ ] MermaidDiagrams 0.8.0 released: the compatibility adapters removed, the comparison with Pele measured again on the Mac and in the iPad and iPhone simulators, the README's table and the Speed items above updated with the numbers, Graphite pinned to `exact: "0.8.0"` and its diagrams checked in the reading view and Live Preview.
