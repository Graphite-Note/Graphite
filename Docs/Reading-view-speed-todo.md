# Reading view speed

## Request

Scrolling the reading view should drop no frame on the iPad and the iPhone. The diagrams speed run of 2026-11-24 (Docs/Native-diagrams-todo.md, Speed, issue #223) made a note full of diagrams scroll without dropped frames by showing its diagrams as pictures; what is left is the reading view's own text blocks, which every note pays for, diagrams or not.

Measured with `DiagramNoteScrollingHostedTests` (a demo note of 35 diagrams under headings and a line of text each, and the same note with each diagram's fence a plain code block, scrolled 30 points a frame by a display link) and `ReadingTextBlockCostHostedTests` (the main thread's work from showing a batch of 24 headings and paragraphs until it is idle), in an iPad Pro 11-inch (M5) and an iPhone 17 Pro simulator of their own, iOS 27.2, Release with testability.

## 1. Text blocks made with less main-thread work

Issue: [#226](https://github.com/Graphite-Note/Graphite/issues/226)

- [x] The selection's gesture recognizers made on first touch. Done 2026-11-24: Textual patch 27 (`UITextInteractionView` adds its `UITextInteraction`, link tap and link gestures the first time a touch, the pointer or a hover finds the view, in `hitTest`, where upstream made a dozen recognizers for every text). A heading or paragraph took 2.1 ms of the main thread to come on screen on the iPad, 1.8 ms after it. Tests: `ReadingLinkFollowingTests`, `PagePreviewCardHostedTests`, `ReadingTasksAndEquationsTests` (synthesized taps, holds and the pointer on links and tags).
- [x] A fragment's text built in its first update, and no geometry readers for overlays it does not need. Done 2026-11-24: Textual patches 28 and 29 (`TextFragment` builds its text in the update that shows it instead of in `onChange` after an empty first layout; rounded backgrounds, attachments and the link tap read the layout only for a text that has them; one block is shown without the block stack); with patch 27 a block costs 1.5 to 1.7 ms (a plain `Text` 0.4 ms; four runs, both simulators). `ObsidianMarkdownParser` resolves the vault folder's links (a file system read) only for a text with a picture of a file. Checked by the hosted tests above and the whole Mac package suite (5,118 tests, 0 failures).
- [ ] A note of code blocks scrolls without dropped frames. The diagram note with its fences as plain code blocks still drops 7 to 18 of 391 frames on the iPad and 4 to 10 of 407 on the iPhone (2026-11-24, 15 to 28 ms of main thread work in the late frames): a code block is Textual's `CodeBlock` with its colored lines, its own horizontal scroll view and the selection's overlay inside it.
- [ ] What SwiftUI spends making a heading or a paragraph, four times a plain `Text`. Ideas, none measured yet: one selection overlay for the whole reading view instead of one view per text (each text makes two UIKit views, and in a frame where one appears the iPad's focus system searches the window, about 2 ms); the text's Markdown parsed off the main actor before it is shown (`FR-103`; 0.05 ms for a one-line block, more for a long paragraph).

Measured again 2026-11-28 (iPad Pro 11-inch (M5) simulator of its own, iOS 27.2, Release with testability, arm64; the Mac under other builds, so a run's numbers move by about a quarter and only numbers of one run are compared):

- A batch of 24 headings and paragraphs, per block: a plain `Text` 0.18 to 0.27 ms; Textual's own `StructuredText` with its default parser and styles 0.95 to 1.4 ms (`testMakingTextualTextsAsAYardstick`, new); the reading view's block 1.6 to 1.8 ms. Textual's text is about 4.5 times a plain `Text` before Graphite adds anything, so the item above is not reached by Graphite's code alone.
- Tried and measured, no gain, not kept: Graphite's Textual styles (line spacing, inline, code, list, heading, table, rule, quote styles, the pictures' loader and link menu) given once to the whole reading view instead of to each text, 1.78 ms against 1.78 ms a block in the same run; Textual's selection turned off, 1.40 ms against 1.42 ms (its gesture recognizers are already made on first touch, patch 27). Graphite's parser costs what Textual's does (1.61 against 1.60 ms).
- Where a block's main-thread time goes (Time Profiler, the batch test): Markdown parsed in `StructuredText`'s body about 8 %, the text's resolution and typesetting about 15 %, the rest SwiftUI making and laying out Textual's views and reading their environment.
- The note of code blocks scrolled: 10 and 17 of 673 frames late in two runs (9 and 16 over 25 ms, at most 25 and 59 ms of main thread work in a frame). Time Profiler over the scroll: Textual's block stack layout (`BlockVStackLayout.sizeThatFits` and `makeCache`) about 10 %, the code block's horizontal scroll view (`ScrollViewLayoutComputer`) 5 %, UIKit views made for each text that appears (`PlatformViewChild`, `UIKitPlatformViewHost`) 7 %, the lazy stack's reduction of the reading highlight's preference (`ReadingHighlightGeometryKey.reduce` from `LazyPreference`) 5 % though nothing was read aloud, the parse 2 %.
- Left: each of these is Textual's structure (a text's views, its block stack, a code block's own scroll view and a UIKit view per text); the reading highlight's preference is observed by the reading view whether or not a word is read, and observing it only while reading would rebuild the view when reading starts.

Steps of 2026-11-28 (same simulator and build settings; each run three times, `-test-iterations 3`; a block's cost compared to a plain `Text` of the same run):

- Before: the code note scrolled with 32, 13 and 25 frames late from the main thread's work (longest work in a frame 37 to 72 ms); a reading block 2.12 to 2.17 ms against a plain `Text`'s 0.34 to 0.37 ms, 6.1 times.
- Step 1, kept (Textual patch 34): the reading highlight's frames go to a `ReadingHighlightReceiver` instead of a preference the lazy stack reduced over every block. The code note: 3, 1 and 0 frames late from the main thread (longest work 48, 20 and 13 ms); a reading block 1.53 to 1.59 ms against 0.35 to 0.40 ms, 4.4 times. Tests: the reading-highlight tests of `ReadAloudReadingViewTests` that use no speech (7) and `HangingAttachmentPlacementTests` on the Mac, `ReadingLinkFollowingTests`, `ReadingTasksAndEquationsTests`, `PagePreviewCardHostedTests`, `PictureZoomAndTabHostedTests`, `LivePreviewTableStripsHostedTests` (17) on the iPad simulator.
- Step 2, measured and not kept: a code block drawn without its horizontal scroll view while its lines fit the column (`Overflow` measuring the code's ideal width, in a scroll view only once wider). The code note: 4, 4 and 2 frames late from the main thread, no better than step 1 alone; reading blocks 1.55 to 1.60 ms.
- Step 3, not built: the UIKit views each text makes are the selection's (the layouts' updater and the interaction overlay); with selection turned off, which removes both, a block cost 1.40 ms against 1.42 ms (2026-11-28, above), so making them only for selectable text has nothing measurable to win.
- Step 4, measured and not kept: Textual's block stack measuring each block once per width (a size cache in `BlockVStackLayout`). The code note: 3, 7 and 2 frames late from the main thread; reading blocks 2.13 to 2.22 ms against plain texts of 0.32 to 0.38 ms in that run, worse than without it. A cache keyed by width alone could also keep a block's height after a picture in it loads.
- After step 1, profiled over the code note's scroll (Time Profiler): no frame late from the main thread's work in that run (9 of 673 over 25 ms with less than 16.7 ms of main thread work, the simulator's drawing); the highlight's preference no longer shows; the most main-thread time goes to platform views appearing (`PlatformViewChild`, 8 %), the block stack's layout (10 %) and the code blocks' scroll views (5 %), none of which the steps above reduced.

- [ ] Checked on a device: the simulators run on the Mac's processor, and the iPad simulator's focus system works as with a hardware keyboard attached.
